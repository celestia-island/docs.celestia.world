# Основная инфраструктура — аутентификация, RPC и фундамент

Каждая платформа, которой вы пользуетесь, стоит на одном и том же фундаменте.
Прочтите эту страницу один раз — и руководства по платформам встанут на свои
места: kirino (аутентификация с нулевым доверием и RBAC), plana (типы
протокола, транспорт JSON-RPC, учёт, движок синхронизации) и hikari
(библиотека UI-компонентов).

## Аутентификация и авторизация (kirino)

- **Идентичность**: хеширование паролей Argon2id; JWT-токены доступа и
  обновления (`TokenManager`, `kirino-session`); ограничение частоты входа и
  блокировка учётных записей.
- **RBAC**: иерархические права (agent.*, system.*, knowledge.*, …),
  разрешаемые через `GrantResolver`; роли объединяют права (admin видит всё,
  viewer — только чтение). Назначения хранятся в Postgres.
- **Делегирование**: scepter доверяет идентификатору пользователя, который
  передаёт шлюз chest (`X-User-Id` / `user_id`), и использует его только для
  изоляции рабочих пространств — аутентифицирующий слой всегда находится
  выше по потоку.
- **Административная поверхность**: конечные точки администрирования панели
  требуют выделенный `ARONA_ADMIN_TOKEN` и без него работают по принципу
  fail closed.

## Протокол и RPC (plana)

- Весь трафик платформы — это **JSON-RPC 2.0 поверх WebSocket** (а также
  запрос/ответ через HTTP POST `/api/rpc`). Методы именуются
  `<Домен>.<Действие>` — например `Sync.MemoryQueryRequest`, `Cli.Search`,
  `Mcp.CallTool`.
- Сетевые типы живут в plana (`plana-state-sync` / `plana-types`): единый
  источник истины для протокола; нижестоящие репозитории фиксируют
  выпущенный тег.
- Уведомления (без `id`) проталкивают события вроде потоковых фрагментов и
  обновлений панели; запросы несут `id`, который эхом возвращается в ответе.
- Движок синхронизации (`plana-sync`) — дерево состояния с сервером в
  качестве авторитета: клиенты объявляют области видимости, сервер рассылает
  диффы с периодическими полными снимками.

## Учёт и тарификация (plana)

Использование учитывается по каждому API key и тарифицируется из
канонической таблицы (учёт в `plana-llm-provider`): токены промптов и
дополнений, оценка стоимости и контроль квот едины для всех сервисов.

## UI-компоненты (hikari)

Библиотека Vue-компонентов (`@celestia-island/hikari`) предоставляет кнопки,
бейджи, таблицы, модальные окна и диалоги подтверждения, используемые каждым
webUI; страницы платформ компонуют их вместе с plana UI shell. Общие
компоненты должны подниматься сюда, выше по потоку, а не реализоваться
заново в каждом репозитории.

## Правила зависимостей

- Слой 0: kirino (аутентификация) → Слой 1: plana (протокол/фундамент) →
  Слой 2: hikari (UI) → Слой 3: сервисы (arona, chest, entelecheia,
  evernight).
- Сервисы реализуют только бизнес-логику; общая функциональность приходит
  из вышестоящих слоёв. Межрепозиторные зависимости используют git-ссылки
  или зафиксированные теги — никогда локальные пути.

# 계층 구조

생태계가 관리 가능하게 유지되는 이유는 엄격하게 계층화되어 있기 때문입니다.
의존성은 한 방향으로만 향합니다: **하위 서비스는 상위 능력을 소비하고,
일반적인 능력은 결코 다시 구현되지 않습니다.**

## 네 개의 계층

| 계층 | 프로젝트 | 제공하는 것 |
| --- | --- | --- |
| **계층 0 — 인증** | [kirino](https://github.com/celestia-island/kirino) | 제로 트러스트 신원: 인증, 세션, 권한 |
| **계층 1 — 플랫폼** | [plana](https://github.com/celestia-island/plana) | 공유 프로토콜 타입, 전송, 그리고 모든 서비스가 필요로 하는 기반 기능 |
| **계층 2 — UI** | [hikari](https://github.com/celestia-island/hikari) | 모든 웹UI가 공유하는 컴포넌트 라이브러리 |
| **계층 3 — 서비스** | arona, shittim-chest, entelecheia, evernight, [malkuth](https://github.com/celestia-island/malkuth), [lagrange](https://github.com/celestia-island/lagrange) | 비즈니스 로직만. 계층 0–2를 소비하고, 각 제품을 실제 제품답게 만드는 동작을 더합니다 |

## 원칙

1. **두 번 구현하지 않는다.** 코드를 쓰기 전에 묻습니다: kirino에 있는가?
   plana에 있는가? hikari에 있는가? 상위 능력을 다시 구현하는 서비스는
   기능이 아니라 결함입니다.
2. **일반적인 능력은 상위로 간다.** 둘 이상의 서비스가 재사용할 기능은 먼저
   kirino, plana, hikari에 만들어지고, 그다음 소비됩니다.
3. **역방향 의존성은 없다.** 서비스는 kirino/plana/hikari에 의존하고,
   plana는 kirino에 의존할 수 있으며, kirino는 plana나 hikari에 절대
   의존하지 않습니다.
4. **소비하기 전에 상위를 확장한다.** 상위에 필요한 능력이 없다면 상위를
   확장한 뒤 소비합니다. 새 능력을 서비스에서 먼저 프로토타이핑하고 나중에
   다시 구현하는 일은 없습니다.
5. **저장소 간 의존성은 git 참조다.** 모든 저장소는 `master` 브랜치에 대한
   git 참조(또는 고정된 버전)로 상위를 소비하고, 로컬 경로 의존성은 쓰지
   않습니다. 모든 저장소는 어느 머신에서든 동일하게 빌드됩니다.

## 왜 중요한가

- **한 번의 수정이 퍼집니다.** kirino의 보안 수정은 재구현물을 뒤지는 대신
  의존성 범프 하나로 모든 서비스에 반영됩니다.
- **리뷰는 위험에 비례합니다.** 계층 3의 변경은 제품 로직이고, 계층 0의
  변경은 인프라입니다 — 리뷰 기준이 그것을 반영합니다.
- **지도는 읽을 수 있게 유지됩니다.** 신규 엔지니어가 이 페이지를 읽으면
  어떤 능력이 어디에 있는지 압니다.
  [프로젝트 지도](../ecosystem/projects.md)가 전체 목록입니다.

# Celestia Island에 기여하기

기여에 관심을 가져 주셔서 감사합니다! Celestia Island는 플랫폼 전체를 아우르는 프로젝트 패밀리입니다 — kirino(인증), plana(플랫폼), hikari(UI), 서비스 계층, 그리고 이들을 둘러싼 웹 UI와 사이트까지 말입니다. 본 가이드는 프로젝트 그룹 전체가 공유하는 기여 정책을 다루며, 개별 프로젝트의 빌드·개발 지침은 해당 프로젝트의 저장소와 문서 사이트에 있습니다.

## 기여 정책 (먼저 읽어 주십시오)

이 그룹은 혼합 중요도를 가진 계층으로 구축됩니다 — 계층 0 (kirino, 인증), 계층 1 (plana, 플랫폼), 계층 2 (hikari, UI), 그리고 그 위의 계층 3 서비스 — 따라서 **정확성, 하위 호환성, 안정성이 기여 처리량보다 우선합니다**. 풀 리퀘스트를 열기 전에 이 섹션을 먼저 읽어 주십시오.

- **높은 병합 기준, 공개 로드맵이 아닙니다.** PR을 열었다고 병합된다는 보장은 없습니다. 우리는 의도적으로 소수의 변경만 수용하며, 그것이 아키텍처에 부합하고 리뷰를 통과할 때만 그렇습니다. 이는 설계된 방침이지 무례함이 아닙니다.
- **환영하는 기여:** 결함 보고, 집중적인 수정, 하위 호환을 깨지 않는 기능·프로토콜 필드 추가, 문서 개선, 그리고 코드 작성 전의 설계 논의.
- **일반적으로 병합하지 않는 것:** 요청되지 않은 대규모 재작성, 공유 계약과 프로토콜 표면의 파괴적 변경 (예: Entelecheia 플랫폼 전반에서 공유되는 JSON-RPC 2.0 프로토콜 타입), 사전 설계 논의 없는 아키텍처 변경, 대량의 "vibe-coded" PR, 그리고 하위 계층의 호환성·안전성·보안 기준을 낮추는 모든 것.
- **핵심과 주변부.** 제로 트러스트 인증 코어, 공유 플랫폼 타입, 공유 UI 컴포넌트 라이브러리에는 가장 엄격한 기준이 적용되며 핵심 팀이 유지 관리합니다. 이에 대한 변경 제안은 설계 논의로 시작해야 합니다.
- **CLA 필요.** 수용되는 모든 기여에는 기여자 라이선스 동의서(CLA) 서명이 필요합니다. [`CLA.md`](cla.md)를 참조하십시오. 커밋에는 `Signed-off-by` 행(`git commit -s`)이 포함되어야 합니다.

> **라이선스는 열릴 수 있지만, 병합 기준은 열리지 않습니다.** **2030-01-01**에 그룹의 프로젝트들은 BUSL-1.1에서 각 저장소의 [`LICENSE`](../../../LICENSE)에 명시된 Change License로 전환됩니다 — 현재 대부분 프로젝트는 SySL-1.0. 이는 *코드로 할 수 있는 일*을 넓혀 주지만, 리뷰 기준을 낮추거나 CLA를 없애거나 더 많은 PR을 수용한다는 의미는 **아닙니다**. 기여 정책은 변경일 전후로 동일합니다.

## 보안

보안 취약점은 **공개 이슈로 올리지 마십시오**. 해당 저장소의 GitHub Security Advisories로 비공개 보고하거나 <security@celestia.world>로 이메일을 보내 주십시오. [`SECURITY.md`](security.md)를 참조하십시오.

## 행동 강령

서로를 존중하고, 건설적이며, 포용적으로 대하세요. 우리는 [Contributor Covenant 행동 강령](code-of-conduct.md)을 따릅니다.

## 시작하기

작업할 저장소를 고르고 해당 README와 문서 사이트를 따르십시오. Rust 프로젝트는 `cargo fmt`, `cargo clippy -D warnings`, `cargo test`로 검증하고, 웹 프로젝트는 `pnpm lint`, `pnpm build`, `pnpm test`로 검증합니다. [생태계 지도](../ecosystem/sites.md)에 모든 프로젝트와 문서의 위치가 정리되어 있습니다.

## 풀 리퀘스트 프로세스

1. 저장소의 기본 브랜치에서 포크하고 브랜치를 만듭니다.
1. 큰 변경이나 공유 계약에 영향을 주는 변경은 먼저 이슈로 논의합니다.
1. 원자적 커밋을 만듭니다. 커밋 제목은 하나의 gitmoji 뒤에 마침표로 끝나는 영어 한 문장이 오며, 자세한 내용은 커밋 본문에 담습니다.
1. 푸시하기 전에 프로젝트의 검증이 모두 통과하는지 확인합니다.
1. CLA에 서명하고 모든 커밋에 `Signed-off-by`를 추가합니다.
1. 리뷰 피드백에 대응합니다. force-push는 리베이스할 때만 사용합니다.

## 라이선스 및 CLA

이 그룹의 프로젝트들은 **변경일이 2030-01-01**인 **Business Source License 1.1 (BUSL-1.1)**로 라이선스되며, 변경일에 각 저장소의 LICENSE에 명시된 Change License로 전환됩니다 — 현재 대부분 프로젝트는 **SySL-1.0**. 내부·학술·정부·교육·비상업 용도로는 오늘날 이미 Apache-2.0 또는 MIT와 동등합니다 (각 저장소의 [`LICENSE`](../../../LICENSE)에 있는 Additional Use Grant 참조). 제한된 상업적 용도(호스팅, 재판매, 서비스로서의 리브랜딩)는 변경일까지 별도의 상업 라이선스가 필요합니다.

기여함으로써 귀하는 귀하의 기여가 프로젝트 라이선스에 따라 라이선스되는 것에 동의하고 CLA([`CLA.md`](cla.md))에 서명합니다. CLA는 프로젝트가 예정된 라이선스 경로를 유지하고 향후 라이선싱을 조정할 수 있도록 **재라이선스 권리를 포함한** 허용적 라이선스를 프로젝트에 부여합니다.

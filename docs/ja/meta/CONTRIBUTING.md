# Celestia Island への貢献

貢献に興味をお寄せいただきありがとうございます。Celestia Island はプラットフォーム全体にわたるプロジェクトファミリーであり、kirino（認証）、plana（プラットフォーム）、hikari（UI）、サービスレイヤ、そしてそれらを取り巻く WebUI とサイト群で構成されます。このガイドは、プロジェクトグループ全体で共有される貢献ポリシーを扱います。個々のプロジェクトのビルド手順と開発手順は、それぞれのプロジェクト自身のリポジトリおよびドキュメントサイトにあります。

## 貢献ポリシー（最初にお読みください）

このグループは重要度の混在するレイヤ構造（mixed-criticality layers）として構築されています —— レイヤ 0（kirino、認証）、レイヤ 1（plana、プラットフォーム）、レイヤ 2（hikari、UI）、その上に載るレイヤ 3 のサービス。したがって**正確性、後方互換性、安定性が貢献のスループットよりも優先されます**。プルリクエストを作成する前に、本セクションをお読みください。

- **高いマージ基準であり、公開ロードマップではありません。** プルリクエストを作成しても、それがマージされることを意味するものではありません。私たちが受け入れる変更は意図的に少数に絞られ、アーキテクチャに適合しレビューに合格した場合に限られます。これは設計上の方針であり、無礼によるものではありません。
- **歓迎するもの:** バグ報告、焦点を絞った修正、追加的で（破壊的でない）機能やプロトコルフィールド、改善されたドキュメント、そしてコードに先立つ設計議論。
- **原則としてマージしないもの:** 大規模で一方的な書き換え、共有コントラクトとプロトコルサーフェスへの破壊的変更（たとえば Entelecheia プラットフォーム全体で共有される JSON-RPC 2.0 プロトコル型）、事前の設計議論を経ないアーキテクチャ変更、大量の「バイブコーディング」PR、そして下位レイヤの互換性・安全性・セキュリティの基準を下げるあらゆるもの。
- **コアと周辺。** ゼロトラスト認証コア、共有プラットフォーム型、共有 UI コンポーネントライブラリには最も厳格な基準が適用され、コアチームによってメンテナンスされます。これらへの変更の提案は、設計議論として始めてください。
- **CLA 必須。** 受け入れられるすべての貢献には、署名済みのコントリビューター・ライセンス・アグリーメントが必要です。[`CLA.md`](cla.md) を参照してください。各コミットには `Signed-off-by` 行が必要です（`git commit -s`）。

> **ライセンスはオープンになりますが、マージ基準は変わりません。** **2030-01-01** に、グループのプロジェクトは BUSL-1.1 から、受領者が選択する Apache-2.0 または MIT へ転換します（[`LICENSE`](../../../LICENSE) を参照）。これにより*コードで何ができるか*の範囲は広がりますが、レビュー基準が**下がるわけでも**、CLA が廃止されるわけでも、より多くの PR を受け入れることになるわけでもありません。貢献ポリシーは変更日の前後で変わりません。

## セキュリティ

セキュリティ脆弱性について公開イシューを**作成しないでください**。該当リポジトリの GitHub Security Advisories 経由、または <security@celestia.world> 宛のメールで非公開に報告してください。[`SECURITY.md`](security.md) を参照してください。

## 行動規範

敬意を持ち、建設的で、包摂的に振る舞ってください。私たちは [Contributor Covenant 行動規範](code-of-conduct.md) に従います。

## はじめに

取り組みたいリポジトリを選び、その README とドキュメントサイトに従ってください。Rust プロジェクトは `cargo fmt`、`cargo clippy -D warnings`、`cargo test` で、Web プロジェクトは `pnpm lint`、`pnpm build`、`pnpm test` で検証します。[エコシステムマップ](../ecosystem/sites.md) には、すべてのプロジェクトとそのドキュメントの場所が一覧されています。

## プルリクエストのプロセス

1. リポジトリのデフォルトブランチからフォークし、ブランチを作成します。
1. 大きな変更や共有コントラクトに影響する変更は、まずイシューで議論します。
1. アトミックなコミットを心がけます。各コミットの件名は「1個の gitmoji + ピリオドで終わる1文の英語」とし、詳細はコミット本文に記載します。
1. プッシュの前に、プロジェクトのチェックがすべて通ることを確認します。
1. CLA に署名し、各コミットに `Signed-off-by` を追加します。
1. レビューの指摘に対応します。force push はリベースのための場合に限って行います。

## ライセンスと CLA

このグループのプロジェクトは、**変更日を 2030-01-01 とする Business Source License 1.1（BUSL-1.1）** の下でライセンスされており、同日をもって各プロジェクトは受領者が選択する **Apache-2.0 または MIT** に転換します。内部利用、学術、政府、教育、非商用の各用途では、今日すでに Apache-2.0 または MIT と同等です（各リポジトリの [`LICENSE`](../../../LICENSE) の Additional Use Grant を参照）。制限される商用利用（ホスティング、転売、サービスとしてのリブランド）には、変更日まで別途商用ライセンスが必要です。

貢献することにより、あなたの貢献がプロジェクトのライセンスの下でライセンスされること、およびあなたが CLA（[`CLA.md`](cla.md)）に署名することに同意したものとみなされます。CLA は本プロジェクトに対し、**再ライセンスの権利を含む**寛容なライセンスを付与します。これにより、プロジェクトは BUSL→Apache/MIT のライセンス移行路を維持し、将来にわたってライセンスを調整できます。

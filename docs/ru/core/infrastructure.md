# Основная инфраструктура — аутентификация, RPC и фундамент

Каждая платформа, которой вы пользуетесь, стоит на одном и том же фундаменте.
Прочитайте это один раз, и руководства по платформам сложатся в цельную
картину: kirino (аутентификация и RBAC с нулевым доверием), plana (типы
протокола и платформенные средства) и hikari (библиотека UI-компонентов).

## Аутентификация и авторизация (kirino)

- **Идентичность**: хеширование паролей, сессионные токены с коротким временем
  жизни, ограничение частоты входа и блокировка учётных записей. Алгоритмы и
  их параметры описаны в [собственной документации kirino](https://kirino.docs.celestia.world),
  а не здесь.
- **RBAC**: разрешения иерархичны и вычисляются для каждого вызывающего; роли
  объединяют разрешения (администратор видит всё, наблюдатель работает только
  на чтение). Назначения сохраняются в базе данных платформы.
- **Делегирование**: сервис, стоящий за другим, никого не аутентифицирует
  сам — аутентифицирующий слой всегда выше по потоку, а идентичность
  вызывающего передаётся дальше только для изоляции рабочих пространств.

## Протокол и RPC (plana)

- Трафик платформы — это **JSON-RPC 2.0**, по WebSocket для потоковой передачи
  и по HTTP POST для запрос/ответа. Имена методов имеют вид `<Domain>.<Action>`.
- Типы обмена — единственный источник истины для протокола, и они живут в
  plana; нижестоящие репозитории фиксируют выпущенную версию, а не форкают
  копию.
- Уведомления не имеют `id` и передают события, такие как фрагменты
  потоковой передачи и обновления панелей; запросы несут `id`, который
  ответ возвращает обратно.
- Поверхности с большим объёмом состояния везде следуют одному шаблону:
  сервер авторитетен, клиенты объявляют, на что они смотрят, а сервер передаёт
  разницу.

## Учёт и тарификация (plana)

Использование учитывается по каждому API key и тарифицируется по одной
канонической таблице, общей для всех сервисов: токены запроса и ответа, оценка
стоимости и контроль квот — это один и тот же расчёт в каждом продукте.

## UI-компоненты (hikari)

Библиотека компонентов предоставляет кнопки, бейджи, таблицы, модальные окна и
диалоги подтверждения, которые использует каждый webUI, чтобы экран выглядел и
вёл себя одинаково, где бы он ни был встроен. Общие компоненты поднимаются
сюда, а не реализуются заново в каждом репозитории.

## Правила зависимостей

- Слой 0: kirino (аутентификация) → Слой 1: plana (протокол/фундамент) →
  Слой 2: hikari (UI) → Слой 3: сервисы (arona, chest, entelecheia, evernight).
- Сервисы реализуют только бизнес-логику; общие возможности приходят из
  вышестоящих слоёв. Межрепозиторные зависимости используют git-ссылки или
  зафиксированные теги — никогда локальные path-зависимости.

# コアインフラストラクチャ — 認証、RPC と基盤

あなたが使うすべてのプラットフォームは、同じ基盤の上に載っています。この
ページを一度読んでおけば、プラットフォームガイドの全体像が分かります:
kirino（ゼロトラスト認証と RBAC）、plana（プロトコル型とプラットフォーム
基盤）、hikari（UI コンポーネントライブラリ）です。

## 認証と認可（kirino）

- **アイデンティティ**: パスワードハッシュ、短命のセッショントークン、
  ログインレート制限とアカウントロック。アルゴリズムとそのパラメータは、
  ここではなく [kirino 自身のドキュメント](https://kirino.docs.celestia.world)
  に記載されています。
- **RBAC**: パーミッションは階層的で、呼び出し元ごとに解決されます。
  ロールはパーミッションを束ねます（admin はすべてを見られ、viewer は
  読み取り専用）。割り当てはプラットフォームのデータベースに永続化
  されます。
- **委任**: 別のサービスの後ろに位置するサービスは、自分では誰も認証
  しません —— 認証するレイヤは常に上流であり、呼び出し元のアイデンティ
  ティはワークスペースの分離のためだけに引き回されます。

## プロトコルと RPC（plana）

- プラットフォームのトラフィックは **JSON-RPC 2.0** で、ストリーミング
  には WebSocket、リクエスト/レスポンスには HTTP POST を使います。メソッド
  名は `<Domain>.<Action>` です。
- ワイヤ型はプロトコルの唯一の真実の情報源であり、plana にあります。
  下流のリポジトリはコピーをフォークするのではなく、リリース済みの
  バージョンに固定します。
- 通知は `id` を持たず、ストリーミングチャンクやパネル更新といった
  イベントをプッシュします。リクエストは `id` を運び、レスポンスで
  エコーされます。
- 状態を多く持つサーフェスは、どこでも同じパターンに従います: サーバーが
  権威であり、クライアントは何を見ているかを宣言し、サーバーが差分を
  ストリーミングします。

## 計測と価格設定（plana）

利用量は API キーごとに計測され、すべてのサービスが共有する 1 つの正規
テーブルから価格付けされます。プロンプトと完了のトークン、コスト推定、
クォータ執行は、どの製品でも同じ計算です。

## UI コンポーネント（hikari）

コンポーネントライブラリは、すべての webUI が使うボタン、バッジ、
テーブル、モーダル、確認ダイアログを提供します。これにより、画面は
どこにマウントされても同じ見た目と同じ振る舞いになります。共有
コンポーネントはリポジトリごとに再実装するのではなく、ここへ
アップストリームします。

## 依存関係のルール

- レイヤ 0: kirino（認証）→ レイヤ 1: plana（プロトコル/基盤）→ レイヤ 2:
  hikari（UI）→ レイヤ 3: サービス（arona、chest、entelecheia、evernight）。
- サービスはビジネスロジックのみを実装し、共有機能は上流から来ます。
  クロスリポジトリ依存は git 参照または固定タグを使います —— ローカル
  パス依存は決して使いません。
